# 悲观锁、锁等待与死锁治理

> 领域：数据库加锁与竞争治理。本文讲"先占后做、冲突则等待"的加锁路径，与"先做后验、冲突则重试"的乐观并发方案互为镜像。

## 锁定读的两种模式

`SELECT ... FOR UPDATE` 取排他行锁，其他事务既不能修改这些行，也不能再对同样的行加锁定读；`SELECT ... FOR SHARE` 取共享行锁，允许多个读者共存但阻止写入，常用于校验引用关系时保持被引用行不变。

关键区别在于加锁时机：普通快照读不加锁，锁定读把冲突提前到读取那一刻暴露，代价是持锁期间其他事务只能排队。

## 悲观与乐观的分工

乐观路径先算后验，用版本条件在提交时判断是否被抢先，冲突表现为受影响行数为零并触发重试；悲观路径先占后做，冲突表现为等待、超时或死锁。

选择依据是冲突概率与重做代价。冲突率低、重试便宜时乐观更省资源；冲突率高时乐观会退化成反复失败的忙等，加锁串行反而吞吐更稳。行锁不能替代幂等键。

## 行锁与间隙锁

InnoDB 在可重复读下不只锁命中的行，还会用间隙锁（gap lock）锁住索引记录之间的区间，两者合称 next-key lock，目的是阻止其他事务在区间内插入。

后果是范围条件的加锁面积远大于直觉。若 WHERE 条件走不到合适索引，扫描过的记录会被逐个加锁，等价于锁住整张表。加锁前确认执行计划用到了预期索引，是悲观锁调优的第一步。

## 死锁是怎么形成的

死锁的必要条件是两个以上事务各自持有对方还需要的锁并循环等待。最常见的成因是加锁顺序不一致：事务 A 按订单、库存的顺序加锁，事务 B 按库存、订单的顺序加锁，交叉后谁都无法前进。

外键检查、二级索引回主键、以及批量语句的行处理顺序，都会引入不易察觉的隐式加锁顺序。

## 死锁检测与等待图

InnoDB 维护事务间的等待图，检测到环就立刻回滚代价较小的事务并报 `ER_LOCK_DEADLOCK`；PostgreSQL 则在等待超过 `deadlock_timeout`（默认 1 秒）后才启动一次检测。

死锁不是卡住，而是被数据库主动中断的一次失败。应用必须把它当作可重试错误，重新读取最新数据后重跑整段业务逻辑，而不是只重发最后那条语句。两个引擎的共同点是牺牲者由数据库选定，应用无法指定谁必须活下来。

## 固定加锁顺序

预防死锁最有效的手段是让全系统按同一个全序加锁，例如永远按主键升序，或永远先锁 ID 较小的账户。批量更新前先对 ID 排序，能消掉一大类交叉等待。

其次是缩短临界区：事务里不要调用外部接口、不要等待人工确认，把能先算的部分挪到加锁之前。一次只锁真正要改的行，也比宽范围加锁安全。

## 锁等待超时

MySQL 的 `innodb_lock_wait_timeout` 默认 50 秒，对在线接口而言太长，通常按业务超时下调到数秒；PostgreSQL 的 `lock_timeout` 默认 0，表示无限等待，建议在会话或角色级显式设置。

超时与死锁语义不同：超时只说明没等到，数据可能仍在被合法处理，盲目重试会加剧拥塞。重试要有次数上限、指数退避和随机抖动。现场排查时，PostgreSQL 查 `pg_locks` 与 `pg_stat_activity` 的 `wait_event_type` 即可定位持锁者。

## NOWAIT 与 SKIP LOCKED

`FOR UPDATE NOWAIT` 在拿不到锁时立即报错，适合宁可快速失败也不愿排队的交互式操作；`SKIP LOCKED` 则跳过已被别人锁住的行，让每个消费者领到互不重叠的任务：

```sql
SELECT id FROM job_queue
WHERE status = 'pending'
ORDER BY id
FOR UPDATE SKIP LOCKED
LIMIT 10;
```

这是用数据库做任务队列的标准写法。消费者应把领取与状态更新放进同一个事务，避免任务被领走却没有落库。注意 SKIP LOCKED 返回的结果集是不完整的，不能用于统计或对账查询。

## 本文边界

本文只讨论加锁语义、等待与死锁治理。版本条件更新、幂等键与超时后的未知结果属于乐观并发与重复请求去重的主题；各隔离级别分别允许哪些异常、跨行聚合约束为何单靠锁住一行仍会失效，应查阅隔离级别选型与业务并发冲突的内容。
