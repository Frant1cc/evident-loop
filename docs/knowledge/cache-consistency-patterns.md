# Cache-Aside 一致性、热点与失效策略

> 领域：缓存工程。本文区分一致性窗口、缓存击穿、穿透和雪崩，并讨论更新数据库后删除缓存的原因。

## Cache-Aside 读流程

Cache-Aside 由应用先读取缓存，未命中时查询数据库，再把结果写入缓存。缓存不是事实源，数据库通常承担最终持久化。回填应设置过期时间，并防止一个超大对象或异常查询长期占用缓存。

并发未命中时，多个请求可能同时查库和回填。对热点键可使用请求合并、互斥重建或逻辑过期，避免瞬时流量直接击穿数据库。

## 写后删除缓存

常见写流程是先提交数据库，再删除缓存。直接同时更新数据库和缓存看似更及时，但两个并发写请求可能以不同顺序完成缓存更新，使旧值覆盖新值。删除缓存让后续读取从数据库重新建立值，缩小顺序错乱风险。

这仍不是严格线性一致。数据库提交与缓存删除之间存在短暂窗口，删除失败也会留下旧值。高一致性场景可以通过变更日志、Outbox、重试队列或版本号让失效操作最终可靠到达。

## 延迟双删

延迟双删尝试在更新数据库前后删除缓存，并在短暂等待后再次删除，以降低并发旧值回填的概率。等待时长难以准确设置，进程崩溃也可能跳过第二次删除，因此它是概率性工程技巧，不是严格一致性协议。

若使用该策略，第二次删除应由可靠任务执行，并监控失败，而不是仅在请求线程中 sleep。

## 缓存穿透

缓存穿透指请求持续查询本来就不存在的数据，每次都绕过缓存访问数据库。可使用短时间空值缓存、布隆过滤器、输入校验和访问控制。空值过期不能过长，否则真实数据创建后仍可能被旧的“不存在”结果遮蔽。

布隆过滤器可能产生假阳性，但不会产生假阴性；它能过滤明确不存在的键，却不能单独作为授权判断。

## 缓存击穿

缓存击穿通常针对单个高热键：键过期时大量请求同时访问数据库。请求合并只允许一个请求重建，其余等待或读取可接受的旧值。逻辑过期可以先返回带陈旧标识的旧数据，再异步刷新。

互斥锁本身要设置超时并防止持有者崩溃造成永久阻塞。

## 缓存雪崩

缓存雪崩是大量键在相近时间失效，或整个缓存集群不可用，导致请求集中落到后端。缓解方式包括为过期时间加入随机抖动、分批预热、多级缓存、限流、熔断和数据库容量保护。

仅把所有 TTL 统一延长会把风险推迟到下一次集中失效。

## 热点键与大键

热点键会把流量集中到单个分片或网络连接；大键会增加序列化、网络和删除延迟。可按业务维度拆分热点、使用本地只读缓存、限制对象大小并异步删除大键。复制更多副本只能缓解读流量，不能消除频繁写热点。

## 一致性验证

监控缓存命中率不能证明数据正确。应采样比较缓存版本与数据库版本，记录删除失败、回填延迟和陈旧读取比例。涉及余额、权限或库存最终确认时，应明确哪些请求必须绕过缓存读取事实源。
