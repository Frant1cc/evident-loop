# LLM 工具调用协议：Schema、配对与修正

> 领域：Agent 工程。本文聚焦模型与工具之间的消息协议和参数契约，不涉及执行结果的持久化与运行重放。

## 工具 schema 声明

工具向模型暴露的只有三样东西：名称、描述和 JSON Schema 参数定义。模型看不到实现代码，也看不到注释，schema 就是全部接口契约。

```text
name: search_orders
description: 按用户 ID 查询最近 30 天已支付订单
parameters: userId(string, required), limit(integer, 默认 20)
```

`required` 与 `enum` 要尽量写满，因为它们会被转成解码约束，直接减少非法参数。只声明 `type: object` 却不给出属性，等于放弃约束。工具名应采用动词加宾语的形式，让用途一眼可辨，同名工具在一次请求里只能出现一次。

## tool_call_id 配对规则

模型自己不执行工具，它只返回一条 assistant 消息，其中的 tool_calls 数组给出调用意图，每个元素含 id、函数名和字符串形式的参数。运行时执行完毕后，必须为每个 id 追加一条角色为 tool 的消息，并把同一个 id 回填到 tool_call_id 字段。

这是硬性协议：若某个 tool_call 没有对应的 tool 消息，多数供应商会直接判定请求非法，而不是降级处理。裁剪历史时误删其中一条，是这类报错最常见的来源。

## 并行调用与结果顺序

一条 assistant 消息可以同时返回多个 tool_calls，表示这些调用之间没有依赖，可以并发执行。运行时可以并行发起，但回填时必须为每个调用各追加一条 tool 消息，缺一不可。

结果消息的排列顺序通常不必与调用数组一致，模型按 id 配对，但保持同序更利于人工读日志。真正要避免的是把多个结果合并进一条 tool 消息，那会让模型无法判断哪段输出属于哪次调用。

## 参数校验与自我修正

模型生成的参数是一段字符串，可能是非法 JSON，也可能类型不对或缺失必填项。运行时应在执行前按 schema 校验，校验失败不要直接抛给用户，而是把错误内容作为该次调用的结果回填给模型。

错误信息要具体到字段与期望值，例如指出 limit 必须是 1 到 100 的整数而实际收到了中文数字。模型据此重试通常一轮即可修正。自我修正必须设重试上限，否则同一个参数错误会无限循环。

## 工具描述质量

调用准确率的瓶颈往往不在模型能力，而在描述写得含糊。描述应说明这个工具解决什么问题、什么时候不该用它、返回什么形状的数据。

把描述写成“查询数据”，模型无法在三个查询类工具之间做出区分。有效写法是加入排他条件，例如注明仅用于订单查询、查用户资料请改用另一个工具。参数的描述同样重要，日期格式、单位与时区都应写明。

## 工具数量与选择退化

工具数量增加时，选择准确率会先平稳后快速下降。经验上超过二三十个工具后，功能相近的工具开始互相混淆，同时全部 schema 每轮都要占用上下文。

缓解方式是按任务阶段动态裁剪可见工具集，或先用一次检索从工具库里挑出候选再暴露给模型。把多个同源接口合并成一个带 action 枚举参数的工具，通常比并列暴露五个近义工具更稳。

## 强制选择与结构化输出

tool_choice 控制模型是否必须调用工具：auto 由模型自行决定，none 禁止调用，指定具体函数名则强制调用该工具。强制调用常用于第一轮必须检索，或把工具当作结构化输出的载体。

用 schema 约束输出格式，比在提示词里描述 JSON 结构可靠得多。但强制调用会剥夺模型直接回答的机会，在不需要工具的轮次应由运行时把 tool_choice 切回 auto，而不是靠提示词提醒，否则模型会硬凑参数。

## 超时、取消与主题边界

工具执行需要独立超时。超时后仍要给模型回填一条 tool 消息，说明本次调用超时且结果未知，而不是把这次调用从历史里删掉，删掉会破坏配对。取消信号应能穿透到工具实现内部，中止底层请求。

对有副作用的工具，超时不等于未执行，回填措辞要区分确认失败与结果未知。工具结果如何持久化、崩溃后如何复用已完成的调用，属于可恢复运行时的主题；长结果如何截断，属于上下文预算管理的主题。
