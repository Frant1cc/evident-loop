# Redis 失效机制：过期、淘汰与键空间通知

> 领域：缓存引擎。本文只讲 Redis 服务端自身的过期删除、内存淘汰与通知配置，不涉及应用侧的缓存使用模式与一致性窗口。

## TTL 与过期时间设置

Redis 通过 `EXPIRE` 或 `SET key value EX 60` 给键挂上绝对到期时间戳，`TTL` 返回剩余秒数，`-1` 表示键永不过期，`-2` 表示键根本不存在。过期时间保存在独立的 expires 字典里，只登记设置过 TTL 的那部分键。

需要注意 `SET` 默认会清除原有过期时间，而 `EXPIRE` 对已存在的键是覆盖式设置，`PERSIST` 则直接摘掉过期属性。对同一个键反复写入并顺手续期，等于把它悄悄变成常驻键，内存增长只能靠淘汰策略兜底。

## 惰性删除与定期删除

过期键不保证在到期瞬间被清除。惰性删除在访问键时检查时间戳，已过期就返回空并顺带删除；定期删除由 `serverCron` 周期性随机抽样 expires 字典，删掉其中过期的键，过期比例高则继续抽样。

认为键一到期内存就立刻释放是不准确的。冷门且不再被访问的过期键，可能在抽样轮到之前一直占着内存。`hz` 默认为 `10`，决定后台周期任务的执行频率，调高更及时也更耗 CPU。

## maxmemory 与淘汰策略

`maxmemory` 设定实例可用内存上限，触顶后由 `maxmemory-policy` 决定行为。`noeviction` 对写命令返回 OOM 错误而读命令仍可服务；`allkeys-lru` 与 `allkeys-lfu` 在全体键中挑选驱逐对象；`volatile-ttl` 只在带过期时间的键里淘汰剩余时间最短的；`allkeys-random` 则随机选取。

选用 volatile 系列时，若没有任何键设置过过期时间，行为会退化成近似 `noeviction`。把纯缓存实例配成 `noeviction` 是常见事故根源：内存写满后业务写入全部报错，而不是自动腾出空间。

## LFU 计数与衰减

`allkeys-lfu` 用 8 bit 的对数计数器估计访问频率，而不是精确计数。`lfu-log-factor` 默认为 `10`，控制计数器增长速度，访问越频繁增长得越慢；`lfu-decay-time` 默认为 `1` 分钟，控制计数器随时间衰减的节奏。

没有衰减机制时，历史上被刷过一次高频的键会永久占据热点身份，新晋热点反而先被淘汰。衰减让频率统计具备时间窗口语义。`OBJECT FREQ` 可读出某个键的当前计数值，用来验证策略是否按预期工作。

## 键空间通知

打开 `notify-keyspace-events` 后，Redis 会把键事件以发布订阅形式投递到 `__keyevent@0__:expired` 一类频道。配置值是字符掩码，`Ex` 表示只推送过期事件，`KEA` 表示推送全部键空间与键事件通知，默认为空即关闭。

这条通道是尽力而为的：发布订阅不做持久化，订阅方掉线期间的事件直接丢失，而且过期事件是在键被真正删除那一刻才发出，不是到期时刻发出。把它当成可靠延时队列是常见误用。

## 主从复制下的过期键

从库不会自行删除过期键。主库删除后向复制流写入一条显式的 `DEL` 或 `UNLINK`，从库回放该命令才真正移除数据。这样设计让主从内容由同一份命令流决定，避免各自判断时间产生分歧。

在从库上读取逻辑已过期但删除命令尚未到达的键，Redis 会在读路径上返回空值，但键仍留在内存里。因此从库 `dbsize` 可能长期高于主库，这属于预期行为而非数据损坏。

## 集中过期造成的抖动

大批键使用同一个过期时长常量写入时，会在同一秒集中到期，触发定期删除的连续循环，主线程被删除动作长时间占用，表现为读写延迟明显尖刺。缓解办法是写入时给过期时间叠加随机偏移。

对体积很大的键改用 `UNLINK` 交后台线程回收，并开启 `lazyfree-lazy-expire yes` 让过期删除走异步路径。监控上应观察 `expired_keys` 与 `evicted_keys` 的速率突变，二者含义不同不可混谈。

## 边界与相邻主题

本文只描述引擎内部的删除时机、内存上限与配置项，不讨论应用该在什么时机删缓存、先写库还是先删缓存，那属于缓存使用模式与一致性窗口的主题。由缓存组件代理读写并异步回写数据源的模式，以及进程内多级缓存的副本失效，也不在范围内。

内存降不下来或延迟尖刺，通常是引擎侧配置问题。读到旧值或并发覆盖，则出在业务写入顺序上。
