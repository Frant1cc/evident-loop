# 缓存代理读写：Read-Through 与 Write-Behind

> 领域：缓存工程。本文讲由缓存组件自身承担回源与落库职责的几种模式及其取舍，区别于应用代码自行查缓存再查库的做法。

## 责任边界在缓存层

这几种模式的共同前提是：业务代码只面对缓存 API，不再持有访问数据源的分支逻辑。加载器与回写器注册在缓存组件上，未命中时由谁查库、写完由谁落库，全由组件决定。

于是调用方看到的是一个看起来永远有数据的存储视图。这与应用自己判断命中、自己回填的做法在故障表现上差别很大：数据源异常会以缓存调用抛异常的方式暴露，而非业务分支里的查库失败。

## Read-Through 回源加载

Read-Through 指未命中时由缓存层调用注册好的加载函数取回数据、写入自身并返回。Caffeine 的 `LoadingCache` 与 Ehcache 的 `CacheLoaderWriter` 都是这一形态的典型实现。

加载器天然是收敛点，同一个键的并发未命中通常只触发一次真实加载，其余线程等待同一结果，比业务侧各自加锁更容易做对。代价是加载逻辑被搬进缓存配置：超时、重试和降级都在加载器内完成，组件不会替你区分查不到和查失败，把异常缓存成空值往往是错的。

## Write-Through 同步落库

Write-Through 在一次调用里先写数据源再更新缓存，两步都成功才返回。它的价值在于缓存与数据源之间不存在长时间不一致窗口，缓存里的值始终是刚刚落库的那个值。

代价直接体现在写延迟上：每次写请求都要承担一次数据源往返，写吞吐被数据源上限约束。它也不等于事务，若落库成功而缓存更新失败，仍要靠删除缓存或重试来收敛，只是这个窗口比异步方案短得多。

## Write-Behind 异步回写

Write-Behind 也叫 Write-Back，它先写缓存并立即返回，把落库动作放进队列交由后台线程异步执行。写延迟从一次数据源往返降到一次内存写，突发流量被队列削峰，数据源看到的是平滑得多的写入曲线。

这意味着刷写完成前，缓存是唯一持有最新值的地方，事实源角色被临时上移到了缓存。任何绕过缓存直连数据库的旁路查询、报表任务或另一个服务，都可能读到明显落后的数据。

## 合并窗口与批量刷写

Write-Behind 的收益主要来自合并：同一个键在窗口内被写十次，最终只需要落库一次。刷写通常由两个条件之一触发：

```text
flush = (待写条数 >= batchSize) or (最早一条等待时长 >= flushInterval)
```

窗口越长，合并率越高、数据源压力越小，但丢数据窗口和一致性延迟同步变长。窗口是这个模式唯一真正的调节旋钮，应按业务能容忍的丢失时长来定，而不是只盯着数据库负载曲线调。

## 队列积压与丢数据窗口

当数据源变慢或不可用，待写队列会持续增长。有界队列写满后要么阻塞写入让低延迟优势消失，要么丢弃最旧的待写项造成静默丢数据；无界队列则把风险转成堆内存耗尽。

进程崩溃或强制重启时，队列中尚未刷出的数据不会自动恢复，除非把待写项先落到本地日志或消息队列。把 Write-Behind 用在余额、库存扣减、支付流水这类不允许丢失的写路径上，是最典型的误用。

## Refresh-Ahead 预刷新

Refresh-Ahead 在键接近过期且最近仍被访问时，提前发起一次异步加载并替换旧值。请求线程读到的始终是仍然有效的旧值，不必等待回源，过期瞬间的延迟尖刺因此被抹平。

Caffeine 用 `refreshAfterWrite` 表达这一语义，它与 `expireAfterWrite` 的区别是：前者到时触发后台刷新并继续返回旧值，后者到时直接判定条目不可用。只对被访问过的键预刷新，冷键仍然自然过期，这样不会为全量键制造无谓的回源流量。

## 选型取舍与边界

按一致性由强到弱大致是 Write-Through、Read-Through、Write-Behind，按写延迟由高到低恰好相反。读多写少且回源逻辑统一时优先 Read-Through；写密集、可容忍秒级丢失的计数与埋点适合 Write-Behind；强一致的写路径应直写数据源并使缓存失效。

本文不展开缓存引擎自身的过期删除与内存淘汰配置，也不讨论进程内多级缓存里各实例副本如何相互同步，这两类问题请到对应主题的文档中查阅。
