# 进程内缓存与多级缓存的副本失效

> 领域：缓存工程。本文从 JVM 进程内视角讨论本地缓存准入、L1 与 L2 分层以及多实例副本的失效手段，不重复分布式缓存的读写流程。

## 进程内缓存的定位

本地缓存把对象直接放在应用堆内，读取就是一次引用访问，没有序列化也没有网络往返，耗时在纳秒到微秒量级，而访问远端缓存服务多在毫秒量级。它适合体积小、读多写少、允许短暂陈旧的数据，如配置项和限流规则。

它真正的特征不是快，而是每个实例各持有一份独立副本。集群从一个实例扩到五十个，就同时存在五十份可能不一致的数据，后面的问题都由此派生。

## 容量上限与 W-TinyLFU

本地缓存必须设上限，否则等同于一处慢性内存泄漏。Caffeine 用 `maximumSize` 限制条目数，或用 `maximumWeight` 配合 `weigher` 按对象体积计权；Guava Cache 的接口语义相近，但淘汰算法是分段 LRU。

Caffeine 默认的 W-TinyLFU 会在候选键即将进入缓存时，先用 Count-Min Sketch 估算它的历史访问频率，只有高于即将被淘汰的受害者时才准入。这道门槛让一次性扫描流量无法冲刷掉真正的热点，也是它命中率通常优于纯 LRU 的主要原因。

## L1 本地与 L2 分布式

多级结构的典型形态是 L1 放本地、L2 放分布式缓存、再往下是数据源。读取按层依次尝试，命中后逐级回填。L1 承担绝大部分请求量并保护 L2 的连接数与网络带宽，L2 则负责跨实例共享和更大的容量。

分层的关键约束是 L1 的存活时间必须显著短于 L2，一般取秒级到几十秒。因为 L1 没有可靠的跨实例失效通道，短存活时间是最后的兜底收敛手段，给 L1 配几小时等于放弃收敛。

## 副本各自为政

一次数据变更只能清掉发起变更那台机器上的本地副本，其余实例毫不知情。在负载均衡之下，同一用户连续两次请求可能落到不同实例，于是出现刷新一次是新值、再刷一次又变回旧值的抖动，这是最典型的线上投诉。

粘性会话能掩盖现象却不解决问题，实例重启或扩缩容时抖动会重新出现。因此用本地缓存的前提，是业务能接受一个明确写下来的陈旧上界。

## 广播失效

广播失效通过发布订阅或消息主题，把删除某键的通知发给全部实例，每个实例收到后清理自己那一份。发起变更的实例通常也订阅同一主题，省掉额外的本地删除逻辑。

这条通道同样是尽力而为：订阅方重连窗口内错过的通知不会补发，分区期间的实例会保留旧值直到自然过期。所以广播失效只是加速收敛的手段，不能替代存活时间兜底，把它当作强一致同步机制是错误的。

## 代际号失效

代际号不删除任何键，而是把版本号拼进缓存键：

```text
物理键 = generation + ":" + 业务键
```

配置发生变更时把 generation 加一，旧代的键因为再也不会被查询而被淘汰算法自然回收。它的好处是失效动作天然幂等，不依赖每条广播消息都精确送达，实例只要读到新代际号就整体切换。

代价是新旧两代数据会短时间同时占用内存，且代际号本身的传播仍需一次读取或订阅，粒度通常是整个命名空间而非单个键。

## 启动预热与惊群

实例启动时 L1 完全为空，若立刻接入满额流量，大量并发未命中会同时穿透到 L2 甚至数据源。滚动发布时这种冲击会随每一批实例重复出现，容量评估里很容易被漏掉。

缓解手段是在健康检查通过之前加载热点键完成预热，并配合网关的慢启动权重让流量逐步爬升。单键层面则依靠加载器收敛并发，保证同一时刻同一个键只有一个线程真正回源。

## 堆压力与内容边界

本地缓存的对象长期存活，会从新生代晋升到老年代，抬高老年代占用与 Full GC 频率。缓存大对象或深层对象树，容易把停顿从十毫秒级推到百毫秒级。`maximumSize` 限制的是条目数而非字节数，差距大时要改用权重计量。

灰度期间新旧版本并存，若两版对同一键用了不同序列化结构，本地副本因进程隔离互不污染，共享的 L2 却会串味，稳妥做法是推进代际号。本文不涉及缓存引擎内部的过期与淘汰配置，也不展开缓存组件代理读写的模式。
