# 事务隔离级别对照与选型

> 领域：事务隔离。本文沿隔离级别这条轴对照各级允许的异常与实现偏差，不涉及多版本存储与空间回收的底层机制。

## 四级与四类异常

ANSI SQL 用能否发生某些异常来定义级别，可以先记住这份对照：

```text
Read Uncommitted : 允许脏读
Read Committed   : 禁止脏读，允许不可重复读
Repeatable Read  : 禁止不可重复读，幻读取决于实现
Serializable     : 效果等价于某种串行执行顺序
```

标准只规定了脏读、不可重复读、幻读三类，丢失更新与写偏差是后来补充的讨论对象。仅凭级别名称判断业务是否安全，往往从这里开始出错。

## Read Uncommitted

该级别允许读到尚未提交、可能被回滚的数据，即脏读。基于脏读做出的判断可能建立在从未存在过的状态上，一旦对方回滚，下游的账目和缓存都无从修正。

实际系统里它几乎没有正当用途。PostgreSQL 干脆把它当作 Read Committed 处理，MySQL 支持但极少启用。把它当成性能优化开关是常见误解，省下的那点等待远不足以抵消数据不可信的代价。

## Read Committed

只读已提交数据，脏读消失，但同一事务内两次相同查询可能返回不同结果，即不可重复读；行数变化则表现为幻读。多数数据库把它设为默认级别，因为它冲突少、等待短。

它的典型陷阱是先查后写：查询与更新之间的窗口里状态可能已被别人改掉。这里应依赖原子条件更新或显式加锁，而不是升级隔离级别。

## Repeatable Read 的两种口径

同名不同义是最容易踩的坑。MySQL InnoDB 的 RR 用一致性读加 next-key lock，能挡住大部分幻读，但普通读与锁定读看到的版本可能不一致。

PostgreSQL 的 RR 实际是快照隔离：整个事务共享一个快照，写冲突时直接抛出序列化失败并要求重试，而不是等待。同一段应用代码在两边行为不同，迁移数据库时必须重做并发测试。

## 快照隔离与写偏差

快照隔离让事务从一个一致时点读取，天然避免脏读与不可重复读，写写冲突也能被检测。它的缺口在于：约束涉及多行，而两个事务各自修改的是不同的行。

例如风控要求一组账户的敞口合计不超上限，两个事务在同一快照下都确认还有额度，随后给不同账户加仓，单行都没冲突，合计却越了线。这类异常统称写偏差。

## Serializable 的两条路线

一条是两阶段加锁配合谓词锁或范围锁，把冲突变成等待和死锁；另一条是乐观的 SSI，先让事务像快照隔离一样跑，提交时再判断是否可串行化。

前者延迟更可预测但并发度低，后者吞吐更好但会产生需要重试的失败。两者对外承诺相同：结果等价于某个串行顺序。走哪条路线由数据库实现决定，应用能做的是同时准备好锁等待超时处理和重试循环。

## SSI 与序列化失败

PostgreSQL 的 Serializable Snapshot Isolation 跟踪事务间的读写依赖，为读操作留下谓词锁记录，当依赖图中出现危险结构时中止其中一个事务，返回 SQLSTATE `40001`。

因此应用必须实现重试循环：捕获 `40001` 后重新开启事务、重新读取、重新决策。保留上一轮算好的写入内容直接重放，等于把旧判断强行落库。跟踪开销主要落在读依赖上，把长只读事务声明为 read only deferrable 能减少误判。

## 按不变量选级别

选型不该从最高级最安全出发，而应先写下业务不变量，再问哪一级能保住它。单行金额扣减用 Read Committed 加原子条件更新就够；跨行合计、排班下限这类约束才值得 Serializable 或显式锁。

全局盲目开 Serializable，会把成本转移成大量序列化失败和重试，反而降低可用性。同一个库里按事务分别设置级别是正常做法，但级别变更必须连同并发测试一起上线，只改配置不改代码通常不够。

## 本文边界

本文只沿隔离级别这条轴组织内容。多版本存储如何维护旧版本、清理如何回收物理空间，属于存储引擎与运维的主题；`FOR UPDATE`、间隙锁与死锁的处理手法，以及版本号乐观锁与幂等键的写法，各自另有专门内容。隔离级别给出的是保证下限，不是业务正确性的替代品。
