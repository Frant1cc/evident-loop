# 乐观锁、幂等键与安全重试

> 领域：并发写入与接口可靠性。本文区分版本冲突控制和重复请求去重，两者经常被错误地当成同一机制。

## 乐观锁的目标

乐观锁假设冲突不是每次都会发生，读取时不长期持有数据库锁，写入时通过版本号、时间戳或旧值条件确认数据没有被其他事务修改。典型更新条件为 `WHERE id = ? AND version = ?`。

乐观锁解决的是“我基于旧状态计算的更新是否仍然有效”。它不能识别两个 HTTP 请求是否属于同一个逻辑操作，也不能阻止调用方用新版本重复执行一次合法扣款。

## 幂等键的目标

幂等键用于识别逻辑操作。客户端为一次创建订单、支付或工具调用生成稳定键；服务端以调用者、操作类型和规范化参数为作用域保存处理状态与结果。相同键再次到达时，服务返回已有结果，而不是再次产生副作用。

键不能只使用一个容易碰撞的短字符串。常见唯一范围是 `(tenant_id, operation, idempotency_key)`，并保存请求参数摘要。若同一键对应不同参数，应拒绝而不是复用旧结果。

## 原子占位

危险实现是先查询幂等表，未找到后执行副作用，最后再插入记录。两个并发请求都可能通过第一次查询。安全做法是在业务事务内先插入具有唯一约束的处理中记录，或使用原子 upsert 获取执行权。

记录可以包含 `processing、succeeded、failed、unknown` 等状态。成功结果应持久化，便于重复请求返回相同业务 ID。处理中记录需要租约或超时治理，但不能在状态不明时直接重做高风险操作。

## 超时后的未知结果

调用方超时只说明没有及时收到响应，不代表服务端没有执行。对于支付、发信或外部发布，超时后立即重试可能重复产生副作用。系统应使用相同幂等键查询原操作，必要时调用下游状态查询或进入人工核对。

若下游支持幂等键，应把稳定键继续传递下去；如果不支持，需要在本地记录外部请求 ID，并通过对账或补偿管理不确定状态。

## 乐观冲突后的重试

版本条件更新返回零行时，调用方应重新读取最新数据并重新验证业务规则。重试不能沿用旧版本计算出的完整请求体。高竞争热点需要设置最大重试次数、指数退避和 Jitter；持续冲突可能说明数据模型需要分片、排队或悲观串行化。

## 幂等与 Exactly-Once

端到端 Exactly-Once 很难由单个中间件保证。消息系统常提供 At-Least-Once 投递，消费者通过 Inbox 唯一键、业务事务和结果记录实现 Effectively-Once。即使消息代理声称事务性投递，外部数据库、邮件或支付系统仍可能处在不同事务边界。

因此“消息只投递一次”和“业务效果只发生一次”不是同一个命题。

## 过期时间

幂等记录保留多久取决于重复请求可能到达的最长窗口和业务审计要求。过早删除会让迟到重试再次生效；永久保留则增加存储和隐私成本。支付与账务通常需要长期审计，低风险查询缓存可以使用较短时间。

## Agent 工具执行中的应用

Agent Runtime 可以用 `taskId、stepId、attempt、toolName` 与规范化参数哈希生成 executionKey。只读工具的成功结果可以直接复用；有副作用的工具还需要业务幂等键和权限审批。模型生成的新 toolCall ID 不应被当作稳定幂等标识。

任务重放时，如果历史状态为 succeeded，运行时复用结果；若为 running 或 unknown，应先恢复或人工确认，不能假设此前没有执行。
