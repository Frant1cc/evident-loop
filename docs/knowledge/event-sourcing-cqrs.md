# 事件溯源与 CQRS：以事件流作为事实源

> 领域：应用架构。本文聚焦事件作为事实源的存储与重放，以及读写模型分离，与把事件仅当作对外通知的发件箱类文档形成区分。

## 事件即事实源

事件溯源不保存实体的当前状态，只按发生顺序追加一串不可变的领域事件，当前状态是把事件依次折叠出来的派生结果。写入路径只做追加，因此完整保留了变更历史与业务意图。

```text
当前状态 = fold(初始状态, 事件[1..n])
```

把事件溯源理解为给业务表补一张审计日志是不准确的：审计日志丢了不影响业务运行，而事件流一旦丢失，系统再也无法确定实体现在处于什么状态。

## 聚合事件流与版本号

每个聚合根拥有一条独立的事件流，事件按追加顺序编号。写入时带上读取时看到的版本号作为期望值，存储层用 `(aggregate_id, version)` 唯一索引拒绝并发写入，这是事件存储实现乐观并发的标准手段。

聚合边界同时也是一致性边界，一次命令只应修改一个聚合，跨聚合的约束交给流程管理器完成。永不结束的长事件流需要按生命周期切分，否则每次加载都要读取全部历史。

## 快照与重放成本

重放成本随事件数量线性增长，快照通过保存某个版本上的聚合状态来截断重放区间：加载时先取最近快照，再只重放它之后的事件。常见策略是每累积固定条数事件写一次快照，例如每两百条。

快照是随时可以删除重建的缓存，不是事实源。快照结构变化时应当直接丢弃旧快照并从事件重放，而不是迁移快照内容，否则一个错误状态会被永久固化下来。

## 投影与读模型重建

投影订阅事件流，把事件写成便于查询的读模型，例如订单列表、统计汇总或搜索索引。同一份事件流可以同时喂给多个投影，新增查询需求时只要写一个新投影并从头重放，无需改动写模型。

投影必须幂等，因为重建和故障恢复都会重复处理同一事件。每个投影记录自己处理到的位置，重建时清空读模型再从零重放，这种随时可丢弃重建的性质是事件溯源最实用的收益。

## 读写分离与读时延

CQRS 把写模型与读模型分开：命令端负责校验不变量并追加事件，查询端只读投影产出的表。两侧可以选用不同存储和不同数据形状，读端不必再为写端的规范化结构做复杂联表。

代价是投影异步更新带来的读时延，用户提交后立刻刷新，可能看不到自己刚做的修改。常见缓解手段是让命令返回事件版本号，客户端带着该版本等待投影追上，而不是假装读写强一致。

## 事件版本演进

事件一旦写入便不可修改，结构演进只能向前兼容。新增可选字段是最安全的演进方式；重命名或拆分字段则要在读取时把旧版本事件转换成新结构，这个过程称为 upcasting，通常由事件存储在反序列化阶段统一完成。

事件应携带 `event_type` 与 `event_version` 两个字段，消费者按这个二元组分派处理器。删除字段是危险操作，历史事件中它依然存在，任何仍依赖它的旧投影都会在重放时失败。

## 补偿事件与合规删除

写错的事件不能改写也不能删除，只能追加一条语义相反的补偿事件，例如用一次冲正抵消错误扣款。历史因此始终可解释：既能看到错误发生过，也能看到它是何时被谁纠正的。

这与个人数据删除类合规要求直接冲突。常见做法是加密擦除，把个人数据放在事件之外，事件里只留密钥引用，需要删除时销毁密钥，事件序列结构保持完整而内容不再可读。

## 与发件箱模式的边界

两者都产生事件，地位却完全不同。事件溯源中事件本身就是事实源，业务表可以整张删掉再由重放重建；发件箱模式的事实源仍是业务表，事件只是提交后对外发出的通知，删掉发件箱表不会丢失任何业务数据。

因此本文不涉及双写窗口、发布器重复发送与补偿编排，那属于跨系统事务与发件箱主题；消费端如何对重复事件去重，请看消费端幂等主题。
