# Agent 上下文窗口管理：预算、压缩与污染

> 领域：Agent 工程。本文聚焦一次运行内向模型上下文放入什么与如何压缩，不涉及执行状态持久化与崩溃恢复。

## 上下文预算分配

上下文窗口是一次运行中最稀缺的资源，应当像内存一样显式分配，而不是先到先得地被历史消息填满。可落地的做法是按用途切分写成配置常量：

```text
budget = system(5%) + tools(15%) + history(35%) + evidence(30%) + output(15%)
```

输出预留必须最先扣除，否则模型会在生成中途被 `max_tokens` 截断，产出半截 JSON。工具定义随注册表增长而膨胀，是每轮重复传输的固定开销，应单独计量，不能混入历史配额。超支时应先压缩历史，再削减证据条数，最后才动系统提示。

## 历史压缩与滚动摘要

历史超出配额时，先淘汰最旧的完整轮次，再对被淘汰内容生成滚动摘要，把摘要作为一条系统消息插回时间线开头。摘要应保留用户目标、已确认结论、失败过的路径与未决问题，丢弃寒暄和重复确认。

压缩是有损操作，阈值不宜太低。常见做法是历史占用达到配额八成才触发压缩，并保留最近两到三轮原文不动，因为最近轮次直接决定下一步动作。

## Working Memory 与 Task Memory

Working Memory 指当前轮次真正送进模型的消息序列，生命周期只有一次请求；Task Memory 指跨轮次沉淀的结构化事实，例如已确定的参数、用户偏好和领域约束。

分层的价值在于：任务记忆可以被精确改写与删除，而摘要一旦写进对话历史就很难撤回。组装工作记忆时应按相关性从任务记忆挑选注入，而不是整块拼进去。条目应带写入轮次与来源，过期偏好要主动清理，否则它会以事实的身份长期留在提示里。

## 工具结果截断策略

工具返回的日志、查询结果或网页正文经常单条就超过配额。截断应保留头部与尾部并在中间插入省略标记，同时附带原始规模，例如 `[truncated: 12480 chars, head 800 + tail 400]`。

关键规则是截断后保留完整原文供追溯：完整结果写入外部存储并返回一个引用 ID，模型若判断需要更多细节，可再调一次读取工具按偏移量取回。把截断掉的内容直接丢弃，会让后续审查无法验证结论来源。

## 中间信息丢失

长上下文中位于序列中部的信息更容易被忽略，这一现象常称为 lost in the middle。它不是传闻，而是把同一份材料换个位置重测就能稳定复现的效应。

应对方式是关键信息置顶或置底：任务指令与硬性约束放在最前，本轮最相关的检索证据与当前待办放在最后一条用户消息附近。不要在按相关性排完序后，又按原文顺序还原并塞回中部。证据条数越多，中部被稀释得越厉害。

## 多轮引用去重

多轮检索容易把同一段落反复注入。组装上下文前应按 chunkId 或内容哈希去重，并记录该证据首次出现的轮次，重复命中时只保留一次并在提示中标注它已被引用过。

去重还要处理部分重叠：不同粒度的片段可能包含同一句话。可按字符区间合并同一文档的相邻片段，再重新计算占用，避免单个来源挤占全部证据配额。去重表随会话存在，任务切换后应清空。

## 上下文污染

上下文污染指错误信息进入历史后被摘要固化，随后在每一轮被反复传播。典型链路是工具返回过期数据、模型据此下结论、结论写入滚动摘要、原始工具消息被淘汰，错误再也找不到出处。

防治手段是为摘要中每条结论标注来源轮次与证据 ID，允许后续轮次显式作废某条结论。只在对话末尾追加一句纠正、却不清除被污染的摘要，通常不足以阻止错误继续传播。

## 开新会话与主题边界

压缩不是无限可用的。当摘要开始压缩摘要、模型重复询问早已回答过的问题、或任务目标发生实质变更时，应该开新会话而不是继续压缩。迁移时只导出目标、已确认事实与下一步动作。整段复制旧历史，只是把同一份污染换个地方存放。

本文只讨论一次运行内如何组织送进模型的内容。执行进度持久化、崩溃续跑与历史重放属于可恢复运行时的主题；证据如何召回、融合与重排属于检索管线的主题。
