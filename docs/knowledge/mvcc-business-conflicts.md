# MVCC 无法自动解决的业务并发冲突

> 领域：数据库与业务一致性。本文重点解释“查询时有快照”为什么仍可能出现超卖、重复处理和写偏差。

## 快照一致不等于决策正确

MVCC 能让事务读取一个自洽快照，但业务决策可能依赖“从读取到提交期间条件没有变化”。两个事务可以分别读取相同旧状态，各自得出局部合理的结论，随后提交出违反整体业务约束的组合结果。

例如库存为 1 时，两个请求都在快照中读到可售，然后分别创建订单。如果扣减操作没有把“库存仍大于 0”写入原子条件，即使每次读取都符合 MVCC 规则，业务仍可能超卖。

## 丢失更新

丢失更新常见于“先读、在应用中计算、再无条件覆盖”。两个事务都读到余额 100，一个加 10，另一个减 20；若最后分别写入 110 和 80，后提交者可能覆盖前一个结果，正确结果 90 没有出现。

优先使用数据库原子表达式，例如 `balance = balance + delta`。若必须基于旧值计算，可使用版本号条件：

```sql
UPDATE account
SET balance = ?, version = version + 1
WHERE id = ? AND version = ?;
```

受影响行数为 0 表示版本已变化，调用方应重新读取并重新判断，而不是盲目重试旧写入。

## 写偏差

写偏差发生在事务读取多行或聚合条件，却分别修改不同记录。值班系统要求至少一名医生在线，两个医生各自在快照中看到另一人在线，于是分别把自己设为离线。两次写入没有修改同一行，因此行级写冲突未必阻止提交，但最终违反“至少一人在线”的约束。

应对方式包括 Serializable 隔离、显式锁住代表业务约束的共同记录、把约束重新建模为可由数据库唯一约束表达的结构，或在提交前进行可靠的冲突检测。

## 条件更新与库存扣减

库存扣减可以把检查和修改合并为一个原子语句：

```sql
UPDATE sku_inventory
SET available = available - :quantity
WHERE sku_id = :skuId AND available >= :quantity;
```

应用必须检查受影响行数。零行表示库存条件不满足，不应继续创建“已支付且待发货”的成功状态。条件更新解决的是并发竞争，不替代请求幂等；相同支付回调重复到达时仍需业务幂等键。

## 唯一约束与幂等记录

“同一订单只能处理一次”适合使用唯一约束，例如 `(tenant_id, idempotency_key)`。处理逻辑和幂等记录应尽量位于同一个事务中。仅在应用内先查询“是否处理过”再插入，会重新引入检查与写入之间的竞争窗口。

唯一约束冲突不是系统异常，它可以是重复请求的正常控制流。服务应读取第一次处理的结果并返回一致响应。

## 锁定读的适用范围

悲观锁适合竞争频繁、临界区短且失败成本高的场景。事务可用 `SELECT ... FOR UPDATE` 锁定需要修改的记录，但必须保持固定锁顺序、缩短事务时间并处理死锁重试。

锁定一行不能自动保护跨行聚合约束。若约束涉及多条记录，需要明确锁住共同的协调对象或提升隔离级别。

## 重试必须重新决策

序列化失败或版本冲突后的重试，应重新读取最新状态并重新执行完整业务判断。只重复最后一次 UPDATE，可能把基于旧快照的决定强行写入新状态。重试还应有次数上限、指数退避和随机抖动，避免高冲突时形成请求风暴。

## 测试业务不变量

并发测试应从业务不变量出发，例如“库存不能为负”“一笔退款只能入账一次”“至少一名值班人员在线”。测试需要同时启动多个事务并控制读取、等待和提交顺序，验证数据库约束、条件更新和重试逻辑是否共同生效。
