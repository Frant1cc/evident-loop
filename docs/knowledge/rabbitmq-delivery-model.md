# RabbitMQ 投递模型：交换机路由与消息确认

> 领域：消息中间件。本文聚焦 AMQP 队列按逐条确认推进的投递模型，与按分区位点推进的日志型消息系统文档形成区分。

## 交换机类型与路由键

生产者只把消息发给交换机，从不直接指定队列，队列收到什么完全由绑定关系决定。direct 要求路由键与绑定键完全相等；topic 以点号分段，支持 `*` 匹配一段、`#` 匹配零到多段；fanout 忽略路由键，把消息广播给所有绑定的队列。

按消息头匹配的 headers 交换机更灵活，但开销更高。如果没有绑定命中，消息会被服务端静默丢弃，除非队列声明了 `alternate-exchange`，或发布时带 mandatory 标志把消息退回生产者。

## 消费确认与重回队列

消费者用 `basic.ack` 告诉服务端可删除该消息；用 `basic.nack` 或 `basic.reject` 拒绝时，若指定重回队列，消息会被放回并再次投递，否则转入死信路径。消费者断开时，它持有的未确认消息会自动入队。

把拒绝后重回队列当成通用失败处理是常见误区：一条永远解析不了的消息会被立即重投，形成占满处理线程的热循环。自动确认模式吞吐最高，但消息一发出即删除，语义等同于至多一次投递。

## 发布确认与事务模式

发布确认是异步的，服务端为每条消息回一个带投递序号的确认，生产者用滑动窗口跟踪未确认消息，吞吐不受往返延迟限制。事务模式用 `tx.select` 与 `tx.commit` 划定边界，每次提交都要同步等待一次往返，吞吐比发布确认低一个数量级。

确认只表示服务端已接收并对持久化队列完成落盘，不表示下游消费者处理成功。这两种机制不能在同一个信道上同时启用，工程上普遍选择发布确认。

## 服务质量与公平分发

`prefetch_count` 限制单个信道上允许存在的未确认消息数量。不设置时服务端会把队列消息一次性轮流派发给所有消费者，慢消费者堆积大量待处理消息，而快消费者提前空转。

取值要在往返空等与分发公平之间权衡：太小会让消费者在等待新消息时闲置，太大则退化为盲目轮询。处理耗时很长的消费者通常设为 1。一个常用的起点是：

```text
prefetch_count = 单消费者并发处理数 × 2
```

## 死信交换机与路由改写

队列可以声明 `x-dead-letter-exchange` 与 `x-dead-letter-routing-key`。消息被拒绝且不重回队列、存活时间到期或队列长度触顶时，都会投递到指定的死信交换机。不设置死信路由键时消息保留原路由键，设置后用新键重新路由。

`x-death` 头部记录了原队列名、死信原因和累计次数，可据此实现有限次重试计数，并在超限后转入人工排查通道。死信队列自身同样需要容量上限，否则问题消息会在无人处理时堆满磁盘。

## 存活时间与延迟队列

队列级 `x-message-ttl` 对该队列所有消息生效，单条消息也可自带过期时间。经典延迟队列做法是让消息先进入一个无消费者、只配存活时间和死信交换机的等待队列，到期后由死信送回业务交换机。

队列只在队头检查过期，因此队头一条长存活时间的消息，会阻塞后面短存活时间的消息按时过期，这是单条过期时间最著名的陷阱。需要任意延迟应改用延迟消息插件。

## 镜像队列与仲裁队列

经典镜像队列依赖主从复制镜像，网络分区恢复后可能整体丢弃某个副本上未同步的消息。仲裁队列基于 Raft 复制，写入需要多数派确认，成员数应取奇数，通常是三个或五个节点，单点故障后已确认的消息不会丢失。

代价是写入延迟更高、内存与磁盘占用更大，并且不再支持优先级、单条消息过期时间等特性。可用性的提升是用功能面和延迟换来的。

## 顺序保证与模型边界

只有单队列配单消费者时，投递顺序才真正成立。多消费者共享队列时处理速度不同，一次重回队列就会把消息排到已取走消息之后，顺序就此破坏。更根本的差异在于队列按逐条确认推进：消息一经确认便从队列中删除，服务端不保留可回放的位点。

本文不涉及分区、位点提交与再平衡，那属于日志型消息系统的投递语义主题；消费端如何吸收重复，请看消费端幂等主题。
