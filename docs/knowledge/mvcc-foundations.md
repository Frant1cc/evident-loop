# MVCC 快照可见性与数据库实现基础

> 领域：数据库并发控制。本文聚焦 MVCC 的版本可见性、快照与垃圾回收，不讨论业务层乐观锁的完整方案。

## MVCC 解决的问题

多版本并发控制（Multi-Version Concurrency Control，MVCC）让数据库为同一逻辑记录保留多个版本。读事务根据自己的快照选择可见版本，因此普通读取通常不必等待写事务释放行锁。它主要改善读写并发和一致性读取，不等于取消锁，也不保证所有并发业务操作都正确。

MVCC 的核心不是“复制整张表”，而是记录版本的创建者、结束标记或指向旧版本的链路。数据库根据事务状态和快照规则判断一个版本是否可见。不同数据库会把旧版本放在数据页、回滚段或独立的版本存储中，但抽象目标相同。

## 事务快照

快照描述事务观察数据时的逻辑时间边界。Read Committed 通常在每条语句开始时获得新快照，因此同一事务的两次查询可能看到不同的已提交结果。Repeatable Read 往往在事务级复用快照，使多次普通读取更稳定，但锁定读、当前读和具体幻读行为仍取决于数据库实现。

快照不是数据副本，它更像一组可见性条件。例如快照可能记录当前活跃事务集合和一个事务 ID 边界：早于边界且已提交的版本通常可见，仍活跃或晚于边界的版本通常不可见。

## 版本链与可见性判断

更新一行时，数据库通常创建新版本并保留旧版本信息。读取者从最新版本沿版本链寻找满足快照规则的版本。版本链过长会增加读取成本，因此频繁更新的热点行可能比静态数据承担更多版本遍历和清理压力。

可见性判断至少要区分：版本是否由当前事务创建、创建事务是否已提交、删除或替换版本的事务是否对当前快照可见。异常终止的事务产生的版本不能作为已提交数据返回。

## MVCC 与锁

MVCC 减少普通快照读与写之间的阻塞，但写写冲突仍需要锁、冲突检测或事务中止。两个事务修改同一物理行时，数据库不能简单保留两个都有效的新版本。`SELECT ... FOR UPDATE` 一类锁定读也会主动获取锁，因为调用者希望基于当前数据执行后续修改。

范围更新、唯一约束检查和外键维护也可能产生锁等待。把 MVCC 描述为“无锁数据库”是不准确的。

## 长事务与版本清理

只要旧快照仍可能读取某个版本，数据库就不能安全回收它。长事务会拉长最老活跃快照的生命周期，导致旧版本堆积、表或版本存储膨胀、垃圾回收延迟，并可能增加复制和备份压力。

治理措施包括限制事务时长、避免在事务中等待人工输入或外部网络、监控最老快照年龄，以及让批处理分段提交。只读事务同样可能阻止版本清理。

## 隔离级别不能只看名称

MVCC 是实现隔离级别的机制之一，不是隔离级别本身。不同数据库对 Repeatable Read、快照隔离和 Serializable 的实现不同。快照隔离可以避免脏读和许多不可重复读，但仍可能发生写偏差；Serializable 可能通过谓词锁、序列化图检测或事务中止提供更强保证。

工程设计应以目标数据库的官方行为和并发测试为依据，不能仅凭“使用了 MVCC”推断业务不变量安全。

## 诊断要点

排查 MVCC 问题时应观察长事务、活跃快照、版本清理进度、死元组或 undo 使用量、锁等待和事务中止率。若问题表现为库存超卖或重复扣减，应进一步检查业务条件更新与幂等设计，而不是只调整垃圾回收参数。
