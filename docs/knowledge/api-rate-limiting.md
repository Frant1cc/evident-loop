# 接口限流算法与工程实践

> 领域：服务端流量控制。本文聚焦限流算法、响应约定与客户端配合，与消息队列的背压和积压治理形成区分。

## 固定窗口的临界突刺

固定窗口计数器给每个时间窗口一个计数，请求到达时自增并与阈值比较，窗口结束归零。实现只需一个计数键和一个过期时间，成本最低，也最容易在网关层落地并水平复制。

缺陷出在窗口边界：限额为每分钟 100 时，客户端在第 59 秒发 100 个请求、第 61 秒再发 100 个，两秒内实际通过 200 个，是标称速率的两倍。这个临界突刺足以打穿按平均值估算的容量，而按均值压测往往测不出来。

## 滑动窗口日志与计数

滑动窗口日志记录每个请求的时间戳，判断时统计最近一个窗口长度内的条目数。它足够精确，能真正杜绝边界突刺，但内存占用与阈值成正比，高 QPS 接口不适用。

滑动窗口计数是折中：把窗口切成若干小格，只保存每格的计数，当前值按上一窗口的重叠比例加权估算。格子越细越接近真实值，存储成本也越高，工程上常见取十格，即以六秒为一格覆盖一分钟窗口。

## 令牌桶与漏桶

令牌桶有速率与容量两个参数，令牌按固定速率注入，桶满则丢弃，请求取到令牌才放行：

```text
tokens = min(capacity, tokens + (now - last) * rate)
```

速率决定长期均值，桶容量单独决定允许多大的瞬时突发，这是它比窗口类算法更好调的原因。漏桶相反，请求先入队再以恒定速率流出，输出被彻底平滑，代价是排队延迟。保护下游恒定处理能力选漏桶，容忍正常业务波峰选令牌桶，两者都不能替代对服务容量本身的扩充。

## 分布式共享计数

多实例部署下各自计数会让实际限额乘以实例数，扩容一倍就等于悄悄放宽一倍限额。共享计数通常放在 Redis，用 Lua 脚本把读取、判断、自增合成一次原子执行，避免检查与写入之间的竞态。

必须为这次远程调用设定毫秒级超时和降级策略：Redis 不可用时是放行还是拒绝，要按接口性质预先决定。核心写接口宜降级为本地限流，只读接口通常直接放行，并把降级次数单独打点。

## 限流维度选择

限流键决定公平性。按 IP 适合匿名流量，但会误伤 NAT 之后的整个办公网；按用户 ID 精确，却在登录之前拿不到；按 API key 或租户适合开放平台，能与合同额度直接对齐，也便于按租户出账。

生产环境往往多层叠加：全局总量保命，租户级保证互不挤占，单接口级防止某个昂贵查询拖垮实例。多层限流应各自独立计数并分别上报命中次数，否则无法判断请求究竟被哪一层拒绝。

## 429 响应与客户端退避

被限流的请求应返回 `429 Too Many Requests`，并在 `Retry-After` 头中给出建议等待的秒数或时间点。把限流响应写成 `503` 是常见错误，它会让调用方误判服务整体不可用。配套返回 `X-RateLimit-Limit` 与 `X-RateLimit-Remaining`，客户端就能在触发拒绝之前主动减速。

客户端收到 429 后立即重试只会加重拥塞。指数退避拉长间隔，但同一批被拒客户端会在同一时刻重试，形成周期性同步冲击，因此必须叠加随机抖动，例如在 `[0, base * 2^n]` 区间内均匀取值。

## 配额型限流与 SLA 归因

速率限流保护瞬时容量，配额限流约束一段周期内的总用量，常与计费绑定：超出套餐后可以拒绝、降速或转入按量付费。两者的窗口长度与处置方式都不同，不应共用同一套计数器。

被限流的请求是否计入可用性 SLA 必须事先写进条款。通行做法是超出约定额度触发的 429 不计入服务方错误，而配置失误导致的误限流计入，监控指标上就要把这两类拒绝分开统计。

## 与熔断和背压的边界

把限流等同于熔断是不准确的。限流按预设阈值拒绝入站请求，保护的是本服务容量；熔断依据下游失败率自动切断调用，保护的是调用链不被拖死；降级则是在压力下返回简化结果。

本文也不涉及消息队列的背压与积压治理，那类机制调节的是异步消费速度与投递可靠性，允许消息滞留后再处理；限流在同步路径上直接拒绝，被拒请求不会被保存，重发的责任完全在客户端。
