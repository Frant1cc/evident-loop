# Kafka 投递语义、消费位点与事务

> 领域：消息系统。本文聚焦 At-Most-Once、At-Least-Once、Kafka Exactly-Once 与业务副作用之间的区别。

## 消息投递语义

At-Most-Once 倾向于先推进消费位点再处理业务，发生崩溃时可能丢失消息，但通常不会重复。At-Least-Once 在业务处理成功后提交位点，确认丢失或进程崩溃会导致重新投递，因此消费者必须处理重复。

工程系统最常见的是 At-Least-Once，因为相较于静默丢失，显式去重通常更可控。投递语义描述消息到达与处理尝试，不直接等同于最终业务效果。

## Consumer Group 与分区

同一 Consumer Group 内，一个分区在同一时刻通常由一个消费者实例处理。增加消费者数量只有在分区足够时才能提高并行度。分区内有序不代表主题全局有序，不同分区之间没有统一消费顺序。

需要保持同一订单事件顺序时，应使用稳定订单 ID 作为分区键。随意改变分区数量或分区策略可能让同一键的新旧消息落入不同分区，需要评估迁移影响。

## Offset 提交时机

若先提交 offset 再写数据库，写库失败后消息可能被跳过。若先写数据库再提交 offset，数据库成功而 offset 提交失败会触发重复处理。这是典型的跨资源一致性问题。

消费者可以在本地数据库事务中同时写业务结果和 Inbox 消息 ID，通过唯一约束让重复消息成为可识别的正常情况。处理成功后再提交 offset。

## 幂等生产者

Kafka 幂等生产者通过 Producer ID 和序列号减少生产者重试导致的分区内重复记录。它保护的是生产者到 Kafka 分区的写入过程，不会自动让下游数据库更新、邮件发送或支付调用具备幂等性。

生产者重启、事务边界和跨系统副作用仍需单独设计。不能因为启用了 `enable.idempotence` 就删除消费者业务去重。

## Kafka 事务与 Exactly-Once

Kafka 事务可以原子地写入多个 Kafka 分区，并把消费位点与新的 Kafka 输出记录放入同一事务。这对“从 Kafka 读取、处理、再写回 Kafka”的流式拓扑很有价值。

如果处理过程同时写入一个不参与 Kafka 事务的外部数据库，Kafka 的 Exactly-Once 不能覆盖该数据库。端到端业务仍需 Outbox、Inbox、幂等键或对账。

## Rebalance

消费者加入、退出或分区变化会触发 Rebalance。处理时间过长、心跳配置不合理或频繁扩缩容可能导致分区反复转移。同一批消息可能在旧消费者尚未完全停止时被新消费者重新获取，因此业务处理必须能承受重复。

批处理应控制单批大小和最大处理时间，在分区撤销回调中停止领取新工作并安全提交已完成进度。

## 失败、重试与死信队列

临时网络错误适合有限重试和退避；数据格式错误或永久业务拒绝不应无限阻塞分区。重试主题可以按延迟级别转移消息，死信队列用于隔离超过策略上限的事件。

死信队列不是垃圾桶。消息应保留原 topic、partition、offset、eventId、错误类型和处理版本，并提供告警、修复和重新驱动流程。

## 监控指标

关键指标包括消费延迟、lag 增长速度、最老未处理消息年龄、处理成功率、重复命中率、Rebalance 次数和死信数量。只观察当前 lag 可能掩盖流量增长下的持续积压趋势。
