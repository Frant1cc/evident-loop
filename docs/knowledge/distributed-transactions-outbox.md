# 分布式事务、Transactional Outbox 与补偿

> 领域：跨系统一致性。本文重点讨论数据库与消息系统双写、Saga 补偿和 Outbox 的边界。

## 双写问题

一个服务先更新本地数据库，再发布消息时存在不一致窗口。数据库提交成功但消息发送失败，下游永远不知道变化；先发消息再提交数据库，则可能出现下游已处理而本地事务回滚。简单交换顺序不能消除问题。

把消息发送放进数据库事务也不安全，因为普通消息代理不参与本地数据库事务，网络等待还会延长锁持有时间。

## Transactional Outbox

Transactional Outbox 在同一个本地事务中写入业务数据和 outbox 事件。后台发布器持续扫描未发布记录，将事件发送到消息代理，再更新发布状态。只要数据库事务提交，事件就不会因为应用在提交后崩溃而永久丢失。

业务表和 outbox 必须位于同一事务资源中。若它们分属不同数据库，原子性问题仍然存在。

## 发布器为何仍可能重复发送

发布器可能成功发送消息，但在标记 outbox 已发布前崩溃。恢复后它会再次发送同一事件。因此 Outbox 通常提供 At-Least-Once 发布，不提供天然的端到端 Exactly-Once。

事件应包含稳定 `eventId`。消费者使用 Inbox 表或业务唯一约束记录已处理 ID，并把去重记录与业务修改放在同一个本地事务中。

## 顺序与分区键

同一聚合根的事件常需要保持顺序，例如订单的 Created 应先于 Cancelled。事件可包含 `aggregateId` 和单调递增 `aggregateVersion`，消息代理使用 aggregateId 作为分区键。消费者发现版本跳跃时可以等待、重试或触发修复。

全局顺序通常昂贵且没有必要，应明确真正需要顺序的业务范围。

## Outbox 清理与积压

发布器需要监控待发送数量、最老记录年龄、失败次数和发布延迟。删除已发布记录前要考虑审计、重放和下游恢复需求。常见做法是归档后分批清理，避免大事务和表膨胀。

如果消息代理长时间不可用，outbox 会增长。系统需要容量预估、限流和降级，不能让积压耗尽主数据库空间。

## Saga

Saga 把跨服务事务拆成多个本地事务，每一步成功后推进下一步，失败时执行补偿操作。例如预订行程时先订机票、再订酒店；酒店失败后尝试取消机票。

补偿不是数据库回滚。取消可能失败、产生费用或无法完全恢复原状态，因此补偿也需要幂等、重试、审计和人工处理通道。

## 编排与协同

编排式 Saga 由协调器明确记录当前步骤和补偿顺序，便于观察复杂流程，但协调器会成为关键组件。协同式 Saga 通过事件让各服务自行响应，耦合表面较低，但流程可能分散、难以追踪并形成事件环。

无论哪种方式，都应持久化状态，而不是仅依赖内存回调。

## TCC 与两阶段提交

TCC 将操作拆成 Try、Confirm、Cancel，需要参与方预留资源并实现幂等确认和取消，适合能够显式冻结资源的业务。两阶段提交依赖协调器和支持协议的资源管理器，可提供更强原子性，但会带来阻塞、可用性和运维成本。

Outbox、Saga、TCC 和两阶段提交不是互相替代的流行词，应根据一致性强度、参与方能力、延迟和失败处理要求选择。
